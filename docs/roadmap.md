# ロードマップ

- **用途**：ReLite の予定のカード。構想の `docs/concept.md` と合わせて企画書として読む。カードは作る段で分けたり足したりし、見直しながら育てる
- **書かないもの**：アカウントや鍵の守り方、サーバーの IP アドレスやアカウントの ID などの伏せる値、個人の名前、前のアプリの弱点（今も公開しているため）。このファイルは公開される
- 決めた経緯は `docs/decisions.md` の「1-3 ロードマップ」の項にある。持ち越しの項目は `docs/ledger.md` の、カードごとの小節にある

## 並べる基準

アプリをほぼ最初から作るので、どの判断と土台を先に置けば後のカードが手戻りしないかで並べた。

- 後から変えたら響く範囲が大きいものを先に
- ほかのものが前提にしているものを先に
- 早く作れば早く分かる危険があるものを先に

**認証と認可を分ける。** 認証（誰か。ログインID で要求の主を見分ける）は、すべてのテーブルが前提にするので先に作る。認可（何をしてよいか）は、まとめて後で作らず、機能を作るカードごとに、その機能の分を一緒に作る。認可を最後にまとめて作ると抜け漏れが生じるリスクが増え、認可の細部は既存の機能を前提にしなければ決められないため。

## 各カードの進め方（コードを作るカード）

- **始め**：Claude Code が前のアプリ（project-lite）の、その機能と画面を洗い出し、前のコードを参照して「どこをどう変えるか」の判断の材料を出す。人と対話AI がその判断を決める。洗い出しは、画面の部品・処理・規則を、1つずつ1行で出す（1つのセルに並べない）。一覧は、洗い出しの全部の行に扱い（残す・改める・捨てる・足す）を付け、行を束ねない。対話AI は一覧を出すときに、洗い出しの行の数と一覧の行の数を並べて示す（2026-11-26、3-2 で一覧からパスワードを見せるチェックボックスを落とした反省から）
- **粒度**：学習のために、1枚のカードで扱う新しい概念を1〜2個までにする
- **確かめることの一覧**：実装の前に、対話AI が確かめることの一覧（ふつうの道と、失敗の道の全部）を作り、人と合意する。依頼文のテストと人のブラウザでの確かめは、この一覧から作る（2026-11-26、3-2）
- **実装の報告**：変えた部分ごとに「前のコードではどう作っていたか／今回どう変えたか／なぜ変えたか」を1〜3行で書く。始めの判断と組にして、統一ログに入れる。作った・変えた・消したファイルの一覧（パス・種別・役目）を載せる。確かめることの一覧の行ごとに、テストのファイル・行・関数名・壊し方・壊したときの結果を並べた表を載せる（2026-11-23、2-3 の振り返りから。2026-11-24・2026-11-26 に直した）
- **実装の後のコミット**：実装の依頼では、コミットと push をしない。変更は作業ツリーに置いたまま報告する。人がエディタとブラウザで確かめ、直しが要れば直してから、人の指示でコミットと push を行う。理由：人がエディタのソース管理の欄で、変わったファイルを見て確かめやすくするため（2026-11-27、3-3a。人の提案）
- **確かめの手順**：実装の報告を受けたら、対話AI が手順を示す。①確かめることの一覧の表で、条件と壊し方を見る ②要のファイルを一緒に読み合わせる（下の形） ③ブラウザで、ふつうの道と失敗の道を試す。1回に3つまで（2026-11-26、3-2 で、実装の報告の後に何をどの順で確かめればよいか人が迷ったことから）
- **読み合わせ（確かめの手順の②）の形**（2026-11-27、3-3a。人の提案と対話AI の足し。3-3a で工程が長く解説を読む段で頭が回らなくなったこと、読む順が前後して人が同じファイルを何度も見直したことから）
  - **回に分ける**：1回で読むファイルは1〜2つにし、1回の中で「読む → 問いを作る → 解説 → 確かめ」を済ませる。人はいつでも切り上げてよく、日を改めてもよい
  - **目当てを1行で示す**：読む前に、そのファイルで掴むことを1行で示す（全部を理解しなくてよくする）
  - **読む順**：処理が通る順（入力の確かめ → 照合などの部品 → コントローラー → 画面）に並べ、1つのファイルは1回で済ませる。目を通すだけの行も、そのファイルの番でまとめて示す
  - **必ず読むのは要のファイル（2〜4つ）だけ**：ほかのファイルは「目を通すもの」として一覧で挙げ、読まなくてもよいものとして扱い、気になったときだけ開く。前のアプリに無い、新しく足した要素は要のファイルに入れる。データの流れと責務の境目を表にし、初めて出る書き方に短い説明を付ける
  - **テスト**：代表の1件だけを「準備・操作・確かめ」の3つに分けた表で読み合わせる。ほかのテストは、関数名と壊し方の表で済ませる（コードは読まなくてよい）。テストは準備の行が多く、中身を捉えにくいため
  - **解説**：結論を先に、1つの問いに2〜3行。足りなければ人が「詳しく」と言い、そこで広げる。表は比べるときだけに使う
  - **各回の終わり**：その回に読んだファイルについて、一言で答える問いを1〜2問出す（覚えているうちに取り違えを見つけて直すため）
  - **見積もり**：分量が大きくなりそうなカード（確かめることの一覧が20行を超えるものなど）は、範囲を決めるときに、確かめを何回に分けるかを見積もって示す
- **振り返り**：人が自分で調べて言語化したものを、振り返りの中で出してもらい、対話AI がレビューして統一ログに入れる。新しい工程にはしない。頭に「行ったこと」を置き、問いごとにヒントを添える。振り返りは言語化を促すことが主であり、短くするのは対話AI の解説の側だけにする。設計の考えの問いに加えて、要のコード・データの流れ・各ファイルの役目を一言で答える問いを3〜5問出す。ファイルをまたぐこと（つながり）を問い、読み合わせの各回の終わりの問い（ファイルの中のこと）と役目を分ける。答えが足りない問いは、対話AI がヒントを足して、人に言い直してもらう（答えを先に出さない）（2026-11-27、3-3a。人の提案。3-3a で対話AI が「行ったこと」とヒントを落とした反省から）
- **Claude Code への直の指示**：依頼ファイルを使わずに直に渡す指示（コミットの指示など）には、終わりに「結果は、対話AI に貼りやすいように、コードブロック1つにまとめて示す」を入れる（2026-11-27、3-3a。人の提案）
- **合意したものは、その場でファイルに書く**：一覧の全行、確かめることの一覧、事前クイズの問い・人の答え・対話AI の補足は、合意したその場で、次に書く依頼ファイルの末尾の「記録の材料」の節に全文を書く（Claude Code は読むだけで、作業には使わない）。理由：3-3a では一覧の全行と事前クイズが会話の中にしか無く、対話AI の会話が圧縮されて失いかけた。人が会話から貼り直して取り戻した（2026-11-27、3-3a）
- **欠点指摘**：Claude Code が `docs/review-criteria.md` の基準でコードを走査してから、対話AI が欠点を指摘する。欠点が見つかるたびに、同じ形の欠点を見つける基準として1行足すかを、人と対話AI で決める
